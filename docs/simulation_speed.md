一个控制步 = 66 个 2 ms 小步。单跑（机器空）每步 0.96 s：开局浅处 0.1–0.5 s，钩放好以后约 1.0 s，颈内段 1.3–1.6 s。每个小步平均 14.3 ms：

## 测法

- **开环重放**：手写推法走 320 步录下动作，每个变体用同一串动作重放，比每步耗时和导丝头轨迹差。重放逐位可复现，差值都是真差别；几个变体同时跑会互相拖慢，所以每批带一个原样重放当参照。
- **混沌底噪**：两个物理上几乎没差别的对照（预判 2 → 2.5 mm；求解精度 1e-4 → 1e-5）重放 320 步后导丝头也差 p95 0.24–1.10 mm、最大 0.8–2.3 mm。开环重放差在这以内的变体分不出好坏，要用闭环多局统计。
- **闭环验证**：手写推法 20 局（种子 1000–1019，`scripts/record_demos.py`）+ 随机推拉 20 局 × 300 步（`runs/speed_validation/random_eps.py`，动作配方同 `tests/test_device_contact.py::random_pushes`），比成功率、受力分布、每小步位移、陷墙深度、出界和 NaN 次数；比较工具 `runs/speed_validation/summarize.py`。结果在 `runs/speed_validation/<变体>_{script,random}/`（不进仓库）。

## 已经装进去的三项

1. **预判范围 2 → 1.0 mm**（`two_devices_real_mass.yaml`，颈内配置继承）。预判距离是加在两边接触距离之上的：2 mm 时套在导管里的导丝点（被导管半径顶在离墙 ≥ 1 mm）也和血管壁登记约束，占导丝接触的三分之一到全部，一个都不受力；1.0 mm 时登记不上，受力的接触数不变。闭环验证（预判 2 / 1.0 / 0.5）：手写推法成功 17 / 17 / 16 局（失败都是手写推法在头臂干末端的老问题，1.0 的失败局和 2 mm 完全相同），三档 120 局 0 出界、0 NaN，受力分布一样（导丝头 p99 0.242 / 0.245 / 0.235 N，导管头最大 3.54 / 3.04 / 2.92 N），每小步位移一样（p99 0.170 / 0.168 / 0.166 mm）。选 1.0 不选 0.5：覆盖范围（预判 + 导丝半径）被最大小步位移超过的次数 3 对 6（17.6k 步里，都没出事），1.0 余量明显些，只慢 10–15 %。
2. **受力回调向量化**（`two_device/labels.py` 的 `window_force_fast`）：同一套算术同样的加法顺序，逐位相同，测试锁住；深处回调 2.1 → 0.9 ms/小步。
3. **两个监控**（不提速，是保险；[`simulator_changes.md`](simulator_changes.md) 问题 24）：每小步器械最远挪多少（标签 `substep_motion`，和预判范围对着看）；每根器械每个点离真实血管网格多远（监控 `wall_distance`、标签 `wall_penetration`），中心线出了网格就把这一局当仿真错误截断（`WallBreach`）。

这三项合计约 **1.5–1.6 倍**（预判 0.5 不再是备选：4 / 6 ms 下它穿墙，见第二轮）。

## 第四项（2026-11-09/10）：开局存档恢复——零件做好、验证过，还没写进训练配置

**问题**：起点课程把一局交给策略时，前面那段（过弓、摆钩，到出管约 230 步）每局都要重新仿真。一局成功的手写推法约 520 步，前 230 步约 190 s、后 290 步约 400 s：开局占一局时间的三分之一；接手后不久就截断的短局里占得更多。用户 11-08 先说"不动"，11-09 晚让先探路、再做成零件并详细验证。省多少：接手点在第 60–165 步，前缀单跑约 20–70 s，一局（接手后 300–500 步，约 2–4 分钟）省 15–30 %；接手后很快截断的短局省得更多。

**为什么能存**：BeamAdapter 每个小步都按两根器械的插入长度重新排节点、重建梁的列表，所以仿真的"状态"只有三样——推进控制器的插入长度、转角、`indexFirstNode`；梁每个节点的位置（含朝向四元数）和速度。接触力求解的热启动表每局重建场景时本来就是空的。**恢复** = 新场景 `reset` 之后把控制器的三样设成存档值，加一个一次性的 SOFA 控制器（排在推进控制器之后、碰撞映射之前），第一个小步控制器排好节点后它把节点位置、速度整个覆盖回去，然后这个小步照常算一次 4 ms 物理（零动作）。不用更短的小步：接触约束是改位置的，0.01 mm 的缝隙在 0.1 ms 里合上就是 100 mm/s 的速度冲击（实测）。裁判（`PhaseDetector`）的段号是走出来的，它的状态（段、段内步数、事件累计、候选段、武装标志、未计的事件）一起存、在它自己 reset 之后装回；截断点用这一局自己的。观测里带记忆的项（上几步动作、前几帧）从头开始，当"策略刚接手"。

**零件**（`guidewire_rl/env/two_device/snapshot.py`，`README.md`"开局存档"一节）：`capture` / `save` / `load` / `restore_simulation`；`env.start` 新类型 `FromSnapshot`（库目录、抽存档的概率 `fraction`、只用裁判段 ≤ `max_phase` 的存档，其余局走 `WireFirst`）；建库脚本 `scripts/make_snapshots.py`（手写推法若干种子，在第 60 步和摆钩 / 转钩 / 回拉 / 坐稳四段的第一步各存一份，`index.json` 列清单）。存档记着物理步长和器械清单，对不上就拒绝；节点数对不上（场景设置变了）也拒绝。段 ≤ 2 的存档不依赖目标（导丝出管前手写推法不看目标），对任何目标都能用；更深的接手点要连目标一起存，没做。

**库**：`runs/snapshots/two_devices_ica/`（不进仓库），种子 1000–1009 × 5 个接手点 = 50 份，每份约 17 KB，10 进程 85 s 建完。接手点的步数：第 60 步（过弓中，裁判 P0）、摆钩 78–80（P1）、转钩 120–123（P1，一个 P2）、回拉 148–155（P2）、坐稳 159–165（P2）。

**验证一：恢复后和原局对得上吗**（`runs/speed_validation/snapshot_check.py`，结果 `snapshot_check/`）：种子 1000–1009 各 5 个接手点（第 60 步、摆钩 / 转钩 / 回拉 / 坐稳四段的第一步），每个点单独从头跑一遍参照到那一步存档，参照走和恢复一样的那一个零动作小步，再录 40 步手写推法的动作、导丝头、受力标签、裁判段；然后新场景恢复、把 40 个动作重放。50 个点、2000 步重放：裁判段 **0** 处不同，0 NaN / 穿墙 / 力闸；节点数全部 191 对上；恢复那一个小步导丝头挪 0.03 mm（中位，最大 0.09）。导丝头和参照的差：第 1 步中位 0.011 mm（最大 0.070），第 40 步中位 0.005（最大 0.056）；40 步里的最大值随接手点变深而变大——第 60 步 0.03、摆钩 0.03、转钩 0.09、回拉 0.20、坐稳 0.24 mm（中位），最大一次 0.76 mm（种子 1007 坐稳点，钩正拉进头臂干、接触最密时中途岔开又合回 0.002）。受力标签差最大 0.138 N（坐稳点）、前三个点 ≤ 0.04 N。这些差都在混沌底噪之内（"测法"一节：物理几乎没差的两个对照重放 320 步也差 p95 0.24–1.1 mm），而且同一种子的手写推法在两次重建的场景里转段步数本来就能差一步（种子 1000 回拉 153 对 154）。从每个点再随机乱推 100 步：50 次全部跑满，受力最大 2.09 N、陷墙 0.016 mm。恢复本身 24 ms（中位）；省掉的前缀 15–51 s（满载机器）。
